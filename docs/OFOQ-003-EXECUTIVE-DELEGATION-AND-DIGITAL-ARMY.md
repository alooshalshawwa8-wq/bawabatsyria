# OFOQ-003 — التفويض التنفيذي وتشكيل القيادة الرقمية

**التاريخ:** 2026-11-14  
**المشروع:** أُفُق / بوابة سوريا  
**المستودع:** `alooshalshawwa8-wq/bawabatsyria`  
**فرع العمل:** `ofoq/ofoq-001-execution`  
**المرجعية:** OFOQ-001 وOFOQ-002، وهذه الوثيقة مكملة لهما ولا تلغيهما.

## 1. التفويض

يتولى المساعد قيادة التنسيق الهندسي والتقني لمشروع أُفُق، وتحديد الأولويات، واستخدام الأدوات والاتصالات البرمجية المتاحة، وتنفيذ أعمال الفحص والتوثيق والاختبار والتغييرات الآمنة على فروع التطوير.

هذا تفويض تشغيلي ضمن حدود الوصول الفعلية للأدوات المتصلة؛ ولا يعني وجود موظفين أو وكلاء مستقلين أو نماذج خارجية تم استقدامها ما لم يتم توصيلها وتشغيلها والتحقق منها فعلياً.

## 2. الهدف التنفيذي

استكمال الموقع الحالي وتحويل وظائفه إلى خدمات موثوقة قابلة للاستخدام والاختبار، مع حماية البنية الحالية والبيانات والإنجازات. لا يتضمن هذا التفويض إطلاق شركات أو منتجات جانبية أو إعادة بناء الموقع من الصفر.

## 3. وحدات القيادة الوظيفية

تُدار المهام وفق التخصصات التالية، ويمكن استخدام أدوات متصلة أو وكلاء مستقلين عند توافرهم فعلياً:

1. **القيادة الهندسية:** تحليل المعمارية، ترتيب الأولويات، مراجعة أثر التغييرات.
2. **هندسة الواجهة وتجربة المستخدم:** الأقسام، التنقل، النماذج، الوصول، الشاشات الصغيرة.
3. **هندسة الخلفية والتكامل:** Edge Functions وواجهات API وتدفق البيانات.
4. **أمن المعلومات:** المصادقة، التفويض، RLS، الأسرار، حدود الثقة، حماية المدخلات.
5. **ضمان الجودة:** اختبارات العقود والمتصفح والهاتف والانحدار.
6. **الأداء والاعتمادية:** القياس، التخزين المؤقت، السجلات، الحصص، معالجة الفشل.
7. **التوثيق والتدقيق:** سجل التغييرات، الأدلة، نتائج الاختبار، والمخاطر المفتوحة.

## 4. الصلاحيات المسموحة دون موافقة إضافية

- قراءة وفحص ملفات المستودع والمشروعات المتصلة، وقراءة سجلات التشغيل والاستشارات الأمنية.
- إنشاء فروع تطوير وملفات توثيق واختبارات وتغييرات كودية قابلة للمراجعة.
- تشغيل اختبارات CI وعمليات التحقق غير الإنتاجية.
- إعداد تقارير هندسية ومصفوفات جاهزية وتوصيات فنية.
- تحسينات محدودة على فرع التطوير فقط، بشرط الحفاظ على الوظائف والبيانات وعدم تغيير إعدادات الإنتاج.
- استخدام البرمجيات والمصادر المجانية فقط في المرحلة الحالية.

## 5. العمليات التي تبقى محجوزة لموافقة المؤسس الصريحة

- أي شراء أو اشتراك أو استخدام خدمة أو نموذج يتطلب دفعاً.
- دمج تغييرات في الفرع الرئيسي أو نشرها إلى الإنتاج.
- تغيير إعدادات Auth أو SMTP أو كلمات المرور أو RLS أو GRANT أو السياسات.
- تعديل الأسرار أو المفاتيح أو نطاقات المواقع أو إعدادات DNS.
- تطبيق migrations أو DDL على قاعدة الإنتاج أو تغيير بياناتها.
- تفعيل الدفع أو الاشتراكات أو تحصيل الأموال أو تغيير بوابات الدفع.
- حذف بيانات أو مستخدمين أو جداول أو فهارس أو وظائف منشورة.
- إعادة نشر Edge Functions أو تغيير إعداداتها التشغيلية.
- إنشاء حسابات اختبار حقيقية أو إرسال رسائل بريد فعلية قبل اعتماد نافذة اختبار مناسبة.

## 6. قواعد التنفيذ

- لا يُعد القسم مكتملاً لمجرد ظهوره أو فتحه؛ يجب إثبات الوظيفة الفعلية باختبار مناسب.
- لا تُحوّل تحذيرات أدوات الفحص إلى تغييرات آلية دون فهم أثرها.
- لا تُنشأ سياسات RLS عامة أو صلاحيات API لإزالة تحذير شكلي.
- لا تُحذف الفهارس لمجرد ظهورها ضمن unused indexes.
- تُراجع التغييرات على فرع تطوير، وتُشغّل الاختبارات، وتُوثق النتيجة قبل اقتراح الدمج.
- يُفصل بوضوح بين ما تم تنفيذه، وما تم اختباره محاكاةً، وما لا يزال يحتاج اختباراً حقيقياً.

## 7. خط الأساس المتحقق منه — 2026-11-14

- فهرس الموقع يحتوي **78 قسماً**. هذا العدد لا يثبت أن جميع الأقسام خدمات متصلة بمصادر حية.
- توجد ثلاث Edge Functions نشطة: `membership-api` الإصدار 23، و`site-assistant` الإصدار 20، و`football-data` الإصدار 45.
- نجح تشغيل GitHub Actions رقم **43596650883** على فرع التطوير، وشمل فحوص العضوية وStripe webhook وJavaScript وعقود البوابة واختبارات المتصفح.
- فحص Supabase Health لم يُظهر تحذيرات في وقت المراجعة.
- Security Advisor أظهر 11 ملاحظة INFO لجداول RLS بلا سياسات، إضافة إلى تحذير WARN واحد لأن حماية كلمات المرور المسرّبة غير مفعّلة. الجداول المذكورة موثقة على أنها خادمية فقط ولا توجد صلاحيات `anon` أو `authenticated` عليها وفق التدقيق السابق؛ لا تُفتح تلقائياً.
- Performance Advisor أظهر 25 فهرساً غير مستخدم. هذه ملاحظات INFO ولا تبرر حذفها دون تحليل عبء العمل وخطط التنفيذ.
- قاعدة البيانات تسجل **36 migration مطبقة**، بينما يحتوي المستودع على **22 ملف migration** فقط. هذا اختلاف يجب حله ومطابقة سجل الهجرات قبل أي تغيير مخطط جديد؛ لا تُنشأ أو تُطبق هجرات إضافية قبل توثيق الفجوة.
- المراجعة المصدرية السابقة رصدت أن محدد الطلبات في `site-assistant` يعتمد على ذاكرة Edge isolate، وأن الثقة بترويسة عنوان IP تحتاج تحققاً من بوابة الاستضافة. كما تحتاج مدخلات بعض مجموعات بيانات كرة القدم إلى مخططات تحقق أدق.
- الدفع ما زال محجوباً بإعدادات التطبيق، ولا يجوز تفعيله ضمن هذا التفويض.
- PR رقم 23 ما زال مفتوحاً بوضع Draft، ولم يتم دمجه أو نشر التغييرات إلى الإنتاج.

## 8. ترتيب الأولويات

1. **تسوية سجل migrations:** تحديد الهجرات الأربع عشرة التي تظهر في قاعدة البيانات ولا يقابلها ملف في المستودع، واستعادة سجل قابل للتدقيق دون إعادة تطبيقها.
2. **تقوية حدود المساعد الذكي:** التحقق من مصدر عنوان IP الموثوق، ثم تصميم حد طلبات دائم مشترك مع اختبار التزامن والفشل المغلق؛ أي تغيير مخطط يبقى ملفاً للمراجعة فقط إلى حين اعتماد المؤسس.
3. **تقوية football-data:** وضع مخططات تحقق دقيقة لكل dataset واختبارات للمدخلات غير الصالحة والحصص والتخزين المؤقت.
4. **استكمال اختبارات الوظائف الأساسية:** تسجيل الدخول والاستعادة والبريد الحقيقي، مع بقاء الاختبار الحقيقي مؤجلاً حتى يحدد المؤسس نافذته.
5. **مراجعة الأقسام الـ78:** تصنيف كل وظيفة إلى محلية، محاكاة، تكامل حي، أو خدمة مكتملة مختبرة؛ ثم إصلاح الأولويات الأعلى أثراً.
6. **تقرير جاهزية تجريبي:** لا يُعلن الإطلاق التجريبي قبل اجتياز الوظائف والأمن وتجربة المستخدم والاعتمادية.

## 9. إثباتات وحدود هذه الوثيقة

هذه الوثيقة تسجل التفويض وخط الأساس والقيود. لا تدّعي استقدام وكلاء مستقلين، ولا تدّعي إغلاق الملاحظات الأمنية، أو اختبار البريد الحقيقي، أو إكمال الوظائف الـ78، أو جاهزية الإطلاق. كل إنجاز لاحق يجب أن يسجل مع رابط التغيير ونتيجة الاختبار وحدود التحقق.
