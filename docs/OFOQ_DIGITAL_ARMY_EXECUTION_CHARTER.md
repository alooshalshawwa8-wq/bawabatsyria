# ميثاق الجيش الرقمي التنفيذي لإمبراطورية أُفُق

**المعرّف:** OFOQ-ARMY-001  
**التاريخ:** 2026-11-14  
**الحالة:** مسودة تنفيذية محفوظة على فرع العمل، بانتظار المراجعة والدمج  
**المرجعية:** الأمر التنفيذي OFOQ-001

## 1. المهمة العليا

تأسيس قوة رقمية تشغيلية من الآن لتصميم وبناء واختبار وتطوير إمبراطورية أُفُق. الجيش ليس مشروع توظيف أو قائمة أسماء، بل منظومة فرق ومسارات عمل متخصصة، تقاس قيمتها بمخرجات قابلة للتحقق. يعمل على أُفُق منذ اليوم الأول، ثم يستخدم الخبرة والبنية والأدوات المكتسبة لبناء المصانع والمنتجات والخدمات الرقمية.

## 2. التسلسل الاستراتيجي الملزم

1. **تشكيل الجيش الرقمي وتجهيزه:** تحديد الاختصاصات، الأدوات، معايير العمل، بيئة التطوير، الاختبار، التوثيق وقياس النتائج.
2. **تطوير أُفُق ورفع جاهزيته للإطلاق التجريبي:** هذه أول مهمة إنتاجية للجيش، ويبدأ العمل عليها بالتوازي مع تشكيل الفرق؛ لا ينتظر اكتمال الهيكل النظري.
3. **إنشاء المصانع الرقمية:** قوالب ومنصات إنتاج قابلة لإعادة الاستخدام، وخطوط تطوير واختبار ونشر موثقة.
4. **إنتاج شركات ومنتجات وخدمات رقمية متكاملة:** إطلاقها تدريجياً بناءً على طلب مثبت، وقيمة واضحة، وتكلفة تشغيل قابلة للقياس.
5. **بناء منظومة اقتصادية رقمية متنامية ومستقلة:** تنويع الإيرادات، وإعادة استثمار الفائض، وتقليل الاعتماد على مورد واحد.

## 3. تشكيل الفرق ومسؤولياتها

هذه اختصاصات تشغيلية افتراضية يمكن تنفيذها بمساعدة الأدوات والأنظمة المتاحة؛ ولا تعني الادعاء بتوظيف أشخاص أو امتلاك وكلاء مستقلين غير متصلين.

- **القيادة والهندسة المعمارية:** ترتيب الأولويات، توحيد المعايير، إدارة المخاطر والقرارات التقنية، ومنع تضارب التغييرات.
- **فريق المنتج وتجربة المستخدم:** تحويل احتياجات المؤسس والمستخدمين إلى مواصفات ومسارات استخدام واضحة، مع اختبار الهاتف وسطح المكتب وإمكانية الوصول.
- **فريق الواجهة والتطبيقات:** تطوير الواجهة، الوحدات، الأقسام، الأداء، التوافق، وإتاحة الاستخدام.
- **فريق الخلفية والبيانات:** تصميم واجهات الخدمات، قواعد البيانات، التكاملات، سلامة البيانات، والصلاحيات.
- **فريق الأمن والخصوصية:** مراجعة المصادقة والجلسات وRLS والأسرار والاعتماديات ومخاطر سلسلة التوريد، وإعداد خطط معالجة قابلة للمراجعة.
- **فريق الجودة والاختبارات:** اختبارات الوحدات والعقود والمتصفح والتكامل والانحدار والأجهزة، مع تقارير قابلة لإعادة التشغيل.
- **فريق التشغيل والاعتمادية:** CI، النشر المنضبط، مراقبة صحة الخدمات، الاستعادة، وإدارة الحوادث دون تغيير إنتاجي غير مصرح.
- **فريق البحث والذكاء الاصطناعي:** تقييم النماذج والمزودين والأدوات، وقياس الجودة والتكلفة والخصوصية، وتفضيل البدائل المحلية أو المجانية حيث تكون مناسبة.
- **فريق المصانع والمنتجات:** تحويل المكونات المشتركة إلى أصول قابلة لإعادة الاستخدام، ثم بناء خطوط إنتاج ومنتجات مستقلة.
- **فريق البيانات والاقتصاد:** قياس الاستخدام والتحويل والإيراد وتكلفة الخدمة وهوامش المساهمة، دون جمع بيانات شخصية غير لازمة.

يمكن إسناد أكثر من اختصاص إلى أداة واحدة عند الضرورة، لكن يجب أن تبقى المسؤوليات ومعايير القبول منفصلة وواضحة.

## 4. العقيدة التشغيلية والمالية

- المجاني أولاً، مع تقييم التكلفة الكلية والقيود ومخاطر الاعتماد قبل اعتماد أي أداة.
- الاستقلال التقني: تفضيل المعايير المفتوحة، وتوثيق قابلية نقل البيانات والخدمات، وتجنب الارتباط غير الضروري بمورد واحد.
- التكامل قبل التكديس: لا تُضاف أداة إذا لم تحل حاجة موثقة أو تحسن نتيجة قابلة للقياس.
- التخصص مع التعاون: لكل مسار مسؤولية ومدخلات ومخرجات ومعيار قبول.
- الاختبارات المستمرة قبل الدمج والنشر، وعدم إعلان جاهزية وظيفة لمجرد ظهور واجهتها.
- سقف الاستثمار المعتمد **100 دولار أمريكي شهرياً كحد أقصى**؛ هذا سقف لا يمثل تفويضاً بالصرف.
- **لا شراء أو اشتراك أو التزام مالي أو ترقية خطة أو تجربة مدفوعة دون موافقة المؤسس الصريحة.**
- **لا حذف بيانات أو حسابات أو سجلات، ولا تغيير حساس في الإنتاج أو Auth أو RLS أو الدفع أو الاستضافة أو النطاقات دون موافقة المؤسس الصريحة.**
- لا تُستخدم بيانات حقيقية أو مفاتيح إنتاج في الاختبارات؛ تُفضّل المحاكاة والبيئات المعزولة.
- تبقى المدفوعات مغلقة حتى استيفاء اختبارات sandbox والضوابط والموافقة الصريحة.

## 5. طريقة التنفيذ

1. جرد الحالة الراهنة والأصول والاختبارات والقيود قبل أي تعديل؛ لا تكرر عملاً منجزاً ولا تفترض أن الاختبار القديم يثبت الحالة الحالية.
2. تحويل كل فجوة إلى مهمة صغيرة ذات مالك وظيفي، وأولوية، ومخاطر، ومعيار قبول، ودليل تحقق.
3. تنفيذ التغييرات في فرع منفصل قابل للمراجعة، مع حفظ التغييرات الصغيرة برسائل واضحة.
4. تشغيل الاختبارات المناسبة وتسجيل النتائج الفعلية، بما فيها الاختبارات الفاشلة والقيود.
5. مراجعة فرق التغيير والأمن والخصوصية والتكلفة قبل طلب الدمج.
6. عدم الدمج إلى الفرع المنشور أو النشر أو تغيير خدمات الإنتاج إلا بعد اجتياز المراجعة والموافقات اللازمة.
7. تحديث سجل الحالة العام ووثائق التشغيل بعد كل إنجاز مثبت.

## 6. لوحة قياس الأداء

لا يُقاس النجاح بعدد الفرق أو الأدوات. تُسجل المؤشرات التالية لكل إصدار أو دورة عمل:

- **الإنتاجية:** المهام المكتملة والمقبولة ÷ المهام المخطط لها، وزمن إنجاز المهمة.
- **الجودة:** نسبة نجاح الاختبارات، وعدد العيوب الحرجة والمفتوحة، ومعدل التراجع بعد النشر.
- **الاعتمادية:** نجاح CI والنشر، وتوفر الخدمات، ومعدل الأخطاء وزمن الاستعادة عند توافر القياس.
- **الأداء:** Lighthouse ومؤشرات Core Web Vitals وحجم النقل، مع فصل قياسات CI عن بيانات المستخدمين الفعلية.
- **الأمن:** الثغرات المفتوحة حسب الشدة، وتغطية مراجعة الصلاحيات والأسرار والاعتماديات.
- **التكلفة:** الإنفاق الفعلي الشهري، وتكلفة كل عملية أو مستخدم نشط عندما تتوفر بيانات موثوقة.
- **القيمة:** الاستخدام الفعلي، إتمام المهام، رضا المستخدمين، والتحويل والإيراد عندما تصبح هذه المقاييس متاحة.

لا تُخترع أرقام عند غياب القياس؛ تُسجل الحالة «غير مقاس» مع خطة قياس.

## 7. أولويات أُفُق التنفيذية الحالية

استناداً إلى سجل الحالة والتدقيق المتاحين في 2026-11-14:

1. استكمال مسار التسجيل وتأكيد البريد واستعادة كلمة المرور باختبار صندوق بريد حقيقي؛ لا يُفتح التسجيل العام قبل نجاحه.
2. اختبار حارس حصة نَبْراس اليومي تحت التزامن واختبار fail-closed في بيئة معزولة؛ لا تُستهلك حصة Gemini الإنتاجية لأغراض الاختبار.
3. مراجعة إعدادات Auth الحساسة، مع إبقاء تفعيل حماية كلمات المرور المسرّبة وأي تغيير إنتاجي معلقاً للموافقة.
4. معالجة فرق سجل ترحيلات Supabase: استعادة ملفات الترحيل الأصلية من مصدر موثوق أو بناء baseline موثق؛ لا تخمين SQL ولا إعادة تشغيل ترحيلات الإنتاج.
5. مراجعة حماية المتصفح والجلسات وسياسة CSP تدريجياً دون كسر الوظائف أو تغيير الاستضافة.
6. استكمال اختبارات runtime لعقود Edge Functions وحدود الطلبات والمدخلات والصلاحيات.
7. استكمال سجل الأدوات الفردي وربط كل أداة من الأدوات الـ78 باختبار وظيفي مستقل، وعدم اعتبار وجود القسم إثباتاً لاكتمال الخدمة.
8. الحفاظ على وضع الدفع المعطل وحظر مزود كرة القدم إلى حين توفر الاعتمادات والموافقات المطلوبة.

## 8. حالة الإنجاز والحوكمة

- هذا الميثاق وثيقة تنظيمية، وليس دليلاً على أن فرقاً بشرية تم توظيفها أو أن كل المهام المذكورة اكتملت.
- كل إنجاز يوصف بأنه مكتمل فقط عند وجود تغيير محفوظ ودليل اختبار أو تحقق مناسب.
- التفويض يسمح بالمبادرة والفحص والإصلاح والتوثيق والاختبار ضمن الأدوات والصلاحيات المتاحة، لكنه لا يلغي حدود الموافقة المالية أو حدود حماية الإنتاج والبيانات.
- عند تعذر التنفيذ بسبب نقص صلاحية أو اعتماد أو موافقة، يوثق العائق بدقة مع أقل إجراء مطلوب لرفعه.
